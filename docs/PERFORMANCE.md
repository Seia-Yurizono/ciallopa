# 本地性能观察：查询与并发流

测量日期：2026-10-23，新加坡时间。当前证据支持继续使用单进程与 SQLite：
100 万条合成记录的完整30天汇总约344毫秒，第一页记录约0.24毫秒。
本轮已让概况与趋势复用同一次查询；现有证据不要求更换数据库或增加聚合存储。
这些是指定机器和负载下的观察，不是生产容量承诺或通用 SLO。

## Usage：100k与1m记录

使用现有 `crates/usage/examples/usage_bench.rs` 生成数据：30天均匀分布，8个账号、4个模型，
随机种子99，约3%带错误码，SSE/WS合成记录混合。数据库分别为6,922,240和68,603,904字节。
每行约69字节来自紧凑字段与共享标签；没有实际请求/输出正文，也没有大量错误详情。
价格表为空；生成器的部分cached值大于input，新缓存统计会按既定口径排除这些不合法样本。
这套数据适合查询成本比较，不代表真实错误、用量、价格或模型延迟分布。

复现基本数据与现有基准，不会删除任何已有路径：

```sh
usage_perf_dir="$(mktemp -d /tmp/ciallopa-usage-perf-XXXXXX)"
cargo build --release --locked -p ciallopa-usage --example usage_bench
/usr/bin/time -v target/release/examples/usage_bench gen "$usage_perf_dir/100k.db" 100000 30 8 4
/usr/bin/time -v target/release/examples/usage_bench query "$usage_perf_dir/100k.db"
/usr/bin/time -v target/release/examples/usage_bench gen "$usage_perf_dir/1m.db" 1000000 30 8 4
/usr/bin/time -v target/release/examples/usage_bench query "$usage_perf_dir/1m.db"
```

现有query模式没有model过滤、count和逐场景RSS，另在临时目录编译了
`query_probe.rs`，直接调用相同release crate的 `Recorder::summary/recent/recent_count`。
它以最后一条记录的开始时间固定查询上界，按 `account,model` 分组；每场景独立进程、连续5次，
下表为5次中位数，包含第一轮。数据刚生成且位于tmpfs，属于暖文件缓存测量。
RSS读取Linux `/proc/self/status` 的 `VmRSS/VmHWM`；峰值是整个查询进程的峰值，
包含Tokio、SQLite、分配器等，不是单个向量，也不是完整网关的RSS。

### 新增指标的成本

只读提取指标改动之前的 `0621c1f` usage源码，和当前usage分别编为临时rlib，
使用相同 `rustc -C opt-level=3`、相同当前core及SQLite依赖、相同probe和1m数据库。
每个场景5次，两轮交换新旧执行顺序；没有修改或覆盖仓库中的usage实现和release二进制。

| 1m / 30天 | 旧实现两轮中位ms | 新实现两轮中位ms | 旧进程峰值MiB | 新进程峰值MiB |
| --- | --- | --- | --- | --- |
| summary | 294.38 / 295.24 | 345.54 / 343.42 | 30.37–30.88 | 43.34–43.47 |
| summary+day buckets | 308.89 / 312.79 | 359.72 / 366.98 | 29.61–30.73 | 43.30–43.77 |

整组新口径在此负载下增加约17%的汇总耗时和13MiB峰值。
它同时增加SQL读取字段、结果分类、缓存/速度采样和流式TTFT向量；这是整组改动比较，
不能将全部差值归因于某一个向量。新旧代码都保留分组样本，再合并到total求精确分位，
样本内存随查询行数增长；本次没有测多浏览器同时查全量窗口的叠加峰值。

### 执行计划与临时索引实验

以实际bundled SQLite运行 `EXPLAIN QUERY PLAN`，当前全部/账号/模型/组合筛选都显示：

```text
SEARCH requests USING INTEGER PRIMARY KEY (rowid>? AND rowid<?)
```

记录页的详情存在性查询额外使用 `error_detail` 主键；未出现临时排序B-tree。
开始时间编码在主键中，时间范围和倒序游标已能利用rowid顺序。
账号/模型没有独立索引，因此其他过滤是在该时间范围扫描后判断。

只在数据库副本添加 `requests(account)`、`requests(model)` 并ANALYZE。
SQLite普通索引已经包含rowid，无需为此次实验重复追加同义的id列。
副本由Python SQLite 3.46.1创建索引和统计；实际查询与计划仍使用bundled SQLite 3.51.3。
这不是生产迁移或写性能测试。

- 副本大小由65.43MiB增至94.20MiB，约增加44%。
- 单account count从32.67ms降至2.61ms，model count从33.36ms降至4.30ms；计划显示covering index。
- account summary仍约76ms；model summary从114ms变为134ms，没有得到普遍加速。
- account+model和account+errors的count仍约33–34ms，需要回表检查另一个条件。
- 未测这些索引对写入吞吐、WAL、清理和磁盘I/O的代价，不将它们直接加入schema。

### 取舍

1. **复用同范围查询。** `/usage/v1/summary` 已能同时返回total、groups和buckets。
   概况与趋势若在一次刷新中各自计算全量summary，会重复扫描并分配分位样本。
   本轮UI已采用一次带bucket的结果服务两块，并在本地demo浏览器验证首次加载仅发一次summary。
   这项UI改动不包含在前面的查询基准中；该基准比较的是单次后端调用。
   改变分桶粒度更新共享查询，不改变时间范围。
2. **暂不添加索引或预聚合。** 单条件count确有优化空间，但当前页面主要成本是完整统计；
   先用真实过滤分布、写入量和持久磁盘测量决定索引及维护策略。
3. **保留准确口径，记录线性内存成本。** 新增样本有可测成本，当前1m测试仍可交互使用。
   若多用户/多窗口汇总成为实际问题，再比较合并样本方式、查询并发限制或可解释的聚合方案，
   不为一次基准设任意最大行数或偷偷改成近似分位。

## 网络：32 / 64 / 128个短流

这组由数据面审视任务执行，脚本为 `/tmp/ciallopa-admission-baseline.py`。
使用release网关与现有 `loadbench` mock：单个虚构账号，plain HTTP loopback，usage关闭，
请求压缩保持默认开启；每条流20个事件，每事件间隔100ms。请求体是loadbench固定的约150字节JSON。
每档重启网关，先完成1次预热请求；并发数等于总请求数，构成一次短突发。
请求超时实际为10秒，脚本外层测量看门狗15秒。

| 并发/总请求 | 失败 | 首输出p50 / p99 ms | 总时长p50 / p99 ms | RSS起点 / 采样峰值MiB | fd峰值 | 网关CPU时间ms |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 32 | 0 | 260.30 / 428.95 | 2182.60 / 2350.97 | 15.25 / 41.85 | 77 | 60 |
| 64 | 0 | 521.81 / 753.05 | 2444.39 / 2673.26 | 15.35 / 57.06 | 141 | 90 |
| 128 | 0 | 1116.08 / 1449.99 | 2951.25 / 3371.08 | 15.47 / 60.84 | 269 | 130 |

RSS/fd每25ms读取 `/proc/<pid>`，可能漏过更短峰值；CPU时间由utime+stime差值计算。
首输出随并发增加，但没有同负载直连mock对照，不能把增加量全部归因于网关。
每档只有一次突发，p99不是稳定尾延迟估计；闭环负载也不能模拟开放到达率过载。
此组不包含大请求体、长上下文、真实TLS、WS turn、慢消费者、usage写入或SQLite查询争用。
因此不据此推出“支持128并发”的部署承诺，也不从三点曲线反推某个正确的默认并发上限。

并发数量上限也不是严格RSS上界：请求体、解压、WS消息及以chunk计数的SSE通道具有不同字节规模。
下一步容量实验应固定这些负载尺寸，并加入直连对照、usage开/关、慢消费/断连和开放到达率。

## 可重复的直连对照

[`scripts/bench-local.py`](../scripts/bench-local.py) 使用Python标准库和现有loadbench，
不自动编译。先在源码稳定时构建一次，再运行：

```sh
cargo build --release --locked -p ciallopa --bin ciallopa --example loadbench
python3 scripts/bench-local.py --build-ref "$(git rev-parse HEAD)"
```

默认32/64并发，每档依次比较直连mock、网关usage关闭、网关usage开启，共6个场景。
每场景启动新的mock/网关、完成1次预热并等网关租约归零，随后总请求数等于并发数；仍是一次短突发。
预热使用同一个假账号，初始化账号状态、池和代码路径；预热和正式负载分别启动loadbench进程，
各自创建reqwest client，所以下游连接不复用。网关可能保留一条预热产生的上游空闲连接，
没有预连接32/64条，也没有测实际池命中率；直连mock的预热客户端连接随该进程退出。
直连使用 `/backend-api/codex/responses`，经过网关使用 `/v1/responses`，loadbench原本就接受完整URL。
两侧使用同一固定逻辑请求体和20个事件、每事件100ms的流；网关保留默认zstd请求压缩，
直连发送明文，所以对照包含这项网关工作，不是完全相同的上游网络字节。
请求整体超时10秒。只有结果需要核对顺序效应时，才用 `--rounds 2` 再运行反序矩阵。

每次运行创建新的 `/tmp/ciallopa-bench-local-*`，保留配置、假账号、各进程日志和JSON结果。
脚本清除代理环境变量与应用测试覆盖变量，所有请求只到loopback，关闭重置卡定时刷新。
退出只对自身保存的子进程句柄发送信号并等待，不按名字kill进程，也不删除任何结果目录。
manifest保存当前HEAD、未提交文件列表、声明的构建版本、二进制哈希、机器和测试参数；
退出时另存子进程PID、启动命令与退出状态。
`--build-ref`是执行者的构建说明；HEAD本身不能证明某个旧二进制来自该提交。

结果保留全部错误数、网关累计拒绝数的增量，以及仅成功请求的首输出/总时长分位。
脚本退出0表示实验完整运行；正式负载是否出现请求错误仍需查看结果中的 `load.errors`，
它不是自动性能门禁。预热或生命周期检查失败则非零退出。
usage开关由本地记录API核对，开启时另存测量后的recorder计数。
mock与gateway资源分别采样；RSS是进程指标，不是整机或每请求内存。
`peak_sampled_rss_kib`为25ms采样峰值，`process_vm_hwm_kib`为进程自启动以来的内核峰值，包含预热。
CPU增量围绕load子进程运行测量，异步usage收尾可能在测量之后继续；不以此声称完整账务写入成本。

最后的 `lifecycle_sanity` 使用cap=1、约4秒流，读取一个字节后暂不继续读：
检查第二个请求为503/gateway_busy、health和admin仍可用、关闭首请求后槽位释放、下个请求可以完成。
它检查的是响应头后仍持有租约和取消释放；小正文不足以产生真实TCP背压，不能当作慢消费者压力测试。
这里的功能等待期限用于让实验结束，不是生产延迟SLO。

`ipv6=true`在此处使builder不再设置该IPv4本地绑定，不代表本次连接使用了IPv6。
这是WSL2、明文loopback下的配置差分，没有修改产品默认值、TLS/HTTP2参数或依赖，
不能据此推荐真实部署改变网络兼容设置。结果在 `/tmp/ciallopa-cold-prepare-probe-und73x7_`，
临时驱动为 `/tmp/ciallopa-cold-prepare-probe.py`。

系统层探针进一步将同步 `socket.bind()` 与异步connect等待分开：本机Python asyncio中，
64个自有AF_INET loopback连接不显式bind时整批约2.64ms；显式bind到 `0.0.0.0:0` 时，
单次bind中位21.84ms、最大33.03ms，64次bind累计1383ms，整批约1389.94ms。
bind到 `127.0.0.1:0` 也类似。原始数据在 `/tmp/ciallopa-bind-connect-probe-vjthwtcc`，
驱动为 `/tmp/ciallopa-bind-connect-probe.py`。
这支持继续核对本机的新连接bind路径；它是单线程Python、无HTTP/TLS的隔离探针，
不能直接换算成Tokio多线程的每请求成本，也不能推广为所有WSL2或生产主机的行为。
探针中connect耗时还包含其他协程同步bind阻塞事件循环的时间，不能将该列误标为纯网络connect延迟。

## 较大请求体与真实背压的小范围观察

使用精确`9111dd0` release（SHA256 `2c6142775ff4…`），固定4并发、usage开启，
分别发送256KiB和1MiB的合法JSON，每种输入各做一次正常读取和暂停读取，共四组。
输入由固定种子的词汇、数字与标识符组成，压缩后为82,747/335,711字节，约原大小的32%；
这是一种合成分布，不代表真实提示词。mock解压、解析并核对输入hash。
每组新进程先用4个小请求暖机，正式请求复用已建立的4条上游连接。

mock收到全部请求体后暂缓响应头，先取准备阶段快照，再释放每条约12.02MiB的SSE流，
其中包含384个32KiB文本delta；未压缩的重复ASCII输出用于制造背压，不代表真实输出的解析复杂度。
暂停组在收到响应头后约1秒不读正文，随后取消一个请求，

这些限制使有限输出也能产生背压，没有修改网关网络参数，不是部署建议。

本次未删除临时目录。Usage与首轮网络的主要文件：

- 网络目录下 `32/result.json`、`64/result.json`、`128/result.json`：完整请求、资源和时长结果。

各场景结果和子进程退出；`lifecycle/result.json`包含功能检查。两组补充探针保留在各自上文所列目录。

这些路径是本次会话的临时证据，不是仓库长期性能服务。持久磁盘冷读、持续写入与查询并发、
高模型/账号基数、价格表复杂度、错误详情较多的库、长时间运行和真实供应商仍未测量。
不要把tmpfs结果套用到低配VPS或机械盘。

2026-10-23通过独立浏览器标签阅读的SQLite官方资料：

- [EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html)：区分SCAN/SEARCH、covering index和临时排序；计划文本仅作诊断，不固化为产品协议。
- [Query Planning](https://www.sqlite.org/queryplanner.html)：rowid顺序可消除排序，多条件索引取决于前缀与选择性，索引并非对所有查询都有收益。
- [ANALYZE](https://www.sqlite.org/lang_analyze.html)：推荐按连接生命周期使用 `PRAGMA optimize`，尤其在增加索引后；统计维护应与将来的索引方案一起评估，不在只读请求里强行执行全量ANALYZE。
