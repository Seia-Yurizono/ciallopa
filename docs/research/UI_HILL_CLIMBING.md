# UI 手动爬坡优化

目标是在反复完成真实任务的过程中，提高界面的易用性、信息层级和视觉一致性。
每轮保留有证据的改善，作为下一轮基线。本方法由人工操作、截图和判断执行，不新增自动测试。
产品语义以 [UI.md](../UI.md) 和 [METRICS.md](../METRICS.md) 为准。

2026-10-31 已按替代模型完成一轮完整实验，见[结果、取舍与证据](UI_HILL_CLIMBING_RESULTS.md)。

分阶段优化、独立评价和保留标准，不照搬自动评估设施、多模型数量、固定轮数或某个分数目标。
模型评分不是用户体验的客观测量。

## 先改善任务体验，再在约束下简化

先把真实用法和失败经历写成可重复的人工验收清单，每条说明起点、操作、预期结果及失败表现。
例如：筛选后能说清作用范围；关闭详情能继续阅读原行；设置保存失败后仍能找到自己的草稿。
过程中发现的新问题补入清单，后续继续复走。本次以手工操作执行这些验收，不要求编写测试程序。

**第一阶段：改善任务体验。** 从可复现的卡点出发，改进理解、入口发现、反馈和恢复。
按每轮流程实施小候选，逐步检查桌面、窄屏、主题、键盘和相关状态，直到本阶段范围内的关键验收通过。
这是任务层面的通过条件，不是要求视觉主观评分满分；发现新失败仍需继续处理。

**第二阶段：在第一阶段基线上简化。** 冻结已经通过的验收要求，再审视重复文案、不必要的边框、
同等强调的次要信息、重复控件和额外操作。每个删减候选都须重走原验收；隐藏关键状态、扩大寻找成本
或丢失恢复入口的删减不保留。工具上下文减少一半是 Theo 那次任务的目标，不转换成“删掉一半 UI”。

第二阶段可交给独立评审上下文，只提供当前界面、任务、验收要求、必须保留的特点和对照证据，
不提供实现者对候选的辩护，也不预告哪版更好。每阶段结束时复走一两个未用于指导本轮改动的相关任务，
检查是否只对选定样例有效。模型可帮助发现问题，实际操作与人工取舍决定是否保留。

## 建立可比较的基线

从仓库根目录运行已有的合成数据演示：

```sh
cargo run --locked -p ciallopa --example ui_demo -- 127.0.0.1:8399
```

打开 `http://127.0.0.1:8399/ui`，演示密钥为 `sk-demo-0123456789abcdef`。
`UI_DEMO_BUSY=1` 增加繁忙数据；`UI_DEMO_READONLY=1` 关闭配置写入。
验证设置保存和草稿时使用默认可写演示，并在记录中注明模式。
如果本机只有 stable，可显式用 `cargo +stable run --locked ...`，同时记录实际工具链版本；
这不改变仓库指定版本。演示使用临时目录与本地假上游，不需要生产数据。

三个 HTML 由 `include_str!` 编译进 Rust，改动后需重新构建、重启。
记录基线提交、相关未提交改动和候选补丁，确保浏览器看到对应版本。回退只撤销本轮补丁。

每个对照固定浏览器版本、中文字体、缩放、时区、主题、视口、演示模式、筛选、展开状态和滚动位置。
初始采用 1440×900 桌面与 375×812 窄屏、深浅主题。布局改动再检查 760、1024、1360px 的切换边界。
窄视口只验证布局；触控目标、软键盘遮挡和手持体验需要真实手机另行确认。

截图时关闭自动刷新、等待加载完成；检查刷新是否打断操作时再开启。
截图按场景一一对应，交互问题补充操作前后画面或短录屏，不靠一张静态图判断交互正确。
图片量以能逐张看清为限；未看到的状态标为未测。

**演示重启不保证数据相同。** 虽然随机种子固定，生成数据仍依赖 `now_ms()`，繁忙场景还受时段影响；
数据目录参数要求目录原先不存在，不能直接重用旧目录。每轮核对实际记录特征、数量、时间窗和列表结构。
相对时间、倒计时等差异单独注明；影响布局或内容密度的差异必须重新找可比场景。
若目标依赖完全一致的数据而暂时无法建立对照，就将该项标为无法判断，不宣称已经改善。

## 每轮执行

1. **观察任务。** 手动走一遍流程，记录找入口时的犹豫、误点、回退、反复滚动和难以解释的状态。
   先列哪些设计有效、需要保留，再按任务阻碍程度和出现频率挑一个问题。
2. **写一个假设。** 说明目标用户、具体页面与状态、拟改区域及预期观察，例如
   “让共享范围与仅请求筛选的作用对象更容易区分”。AI 可提出最多三个候选，每个说明收益和代价；
   选择一个主要假设实施，不因一轮评价扩成全站重设计。
3. **改动并重走。** 保存可逆补丁，重编、重启，确认数据可比；重复同一任务并保留前后证据。
   检查任务完成、入口发现、误操作、反馈清楚程度和中断后的继续操作。
   点击、按键和滚动次数作辅助；减少次数不能以丢失确认、说明或上下文为代价。
4. **独立比较。** 先写下自己的观察，再看 AI 的意见；成对截图可交换 A/B 顺序，隐藏新旧标签。
   从信息层级、阅读负担、控件一致性、留白与对齐评价，要求每条意见有页面和位置。
   截图评审不能替代实际点击、键盘、焦点和滚动检查。未提供参考图时，不让模型凭记忆给竞品排名。
5. **作出取舍。** 写明改善、退化、分歧和未测项。目标问题有可观察改善、相关流程通过且没有重要退化，
   才保留为下一轮基线。收益无法判断时保留原基线，缩小下一轮候选。

对受影响流程，以下问题必须修正或回退：共享范围与列表条件混淆，统计口径或状态被误导，
关键动作不可达，关闭详情丢失合理焦点或阅读位置，窄屏遮住操作，未保存草稿丢失。
每轮手动检查适用的桌面/窄屏、主题、键盘与焦点状态；受影响的加载、失败、空态也要走查。
演示无法复现的情况记录为未测，若它决定本轮是否可接受，就先补齐手动复现场景。

每几轮重新走完整调查流程及受影响的账号、设置页面，发现跨区域累积退化。
同一方向连续两轮没有明确改善时暂停，重新观察问题或收集使用者反馈；不为了提高模型分数无限迭代。

## 第一轮与记录格式

第一轮固定为“发现异常 → 问题分组 → 一条请求详情 → 返回列表”。在实际演示中选择可复现的异常，
记录范围、分组、原因和请求特征，检查是否能理解异常、找到下一步、关闭后继续阅读原列表。
先建立正常与繁忙数据下的基线，再针对观察到的一个阻碍提出候选，不预设当前界面有某个缺陷。

每轮记录随截图放在工作证据目录，不将全部轮次日志堆入产品文档：

```text
阶段（改善任务/约束下简化） / 轮次 / 日期 / 基线版本与工作区状态 / 候选补丁：
本轮验收条目、通过条件、发现的新失败：
目标任务、观察到的问题、假设、必须保留的特点：
演示模式与启动时间 / 筛选 / 浏览器与字体 / 视口与主题：
数据可比性及差异 / 前后截图或录屏路径：
操作过程、卡点、误操作与结果：
改善 / 退化 / 相关语义、键盘、焦点、窄屏和草稿检查：
未测项、原因及是否影响决定：
AI 意见 / 人工验证 / 尚存分歧：
决定：保留、修正或回退；理由及下一轮问题：
```

AI 用于提出有限候选、解释代码影响和检查遗漏。需要独立复核时提供同一任务说明与完整证据，
不预告期望结论；由实际操作和设计取舍决定是否保留。上述来源不构成不同模型或推理强度的对照实验，
不能据此认定某个型号普遍最佳，也不要求每次小改动都开展多模型评审。
